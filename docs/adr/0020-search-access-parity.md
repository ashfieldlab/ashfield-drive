# ADR-0020: 검색 결과는 effective_permission 을 통과한다 (단순 scope 필터 금지)

- 상태: 채택
- 날짜: 2026-07-12

## 맥락

파일 검색(`/api/v1/search`)이 노드를 `scope=='shared'` 조건만으로 반환했다. 그런데
scope=shared 노드라도 실제 접근은 `effective_permission` 이 더 좁게 판정한다:

- **팀 폴더**(부서 바인딩): 그 부서(+하위)만 접근. 아니면 0.
- **vault**(E2E): 생성자·공유받은 사람만.

즉 검색이 접근 판정을 건너뛰어 **팀 폴더(부서 전용) 파일을 비소속 멤버에게
노출**했다(부서 격리 우회 = 유출). 동시에 반대로, 나에게 직접/부서 공유된 **개인
scope 파일은 누락**했다(`scope=personal AND owner=me` 만 봤으므로).

## 결정

**검색은 이름 매치 후보를 `effective_permission(...) > 0` 으로 사후 필터한다.**
정상 접근 경로(`assert_access`)와 같은 함수를 재사용하므로 검색 가시성이 열람
권한과 **구성상 항상 일치**한다.

- 후보를 상한(candidate cap)까지 이름 매치로 뽑고 → 권한 필터 → `limit` 개 반환.

## 대안

- **(A) 순수 SQL scope 술어**: 접근 가능 집합을 SQL 한 방으로.: **기각**: vault/팀폴더
  서브트리 판정 + 부서 소속(외부 디렉터리: 2026-10 이후 비활성, ADR-0023)까지 SQL 로 정확히 표현하기 어렵고, 권한 규칙이
  바뀌면 두 곳(정상 경로 + 검색)을 따로 고쳐야 해 드리프트·유출 재발 위험.
- **(B) 검색 전용 권한 인덱스**(비정규화): 접근 가능 node_id 를 미리 적재.: **기각**:
  현재 규모에 과함. 공유·부서 변경 시 재적재 파이프라인 부담.

## 결과

- 유출 차단 + 개인·부서 공유 파일 포함이 한 번에 해결(권한 함수가 이미 셋 다 판정).
- **성능 trade-off**: 후보마다 재귀 SQL(+부서 share 있으면 외부 디렉터리 1회, 요청당 캐시).
  대부분 후보(개인 소유·일반 shared)는 즉시 판정이라 실사용 무리 없음. 규모 커지면
  (B) 재검토.
- FTS/트라이그램(ILIKE 대체)은 별도 항목으로 보류: 접근 정합성과 독립.
