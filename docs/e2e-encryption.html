🔒 보안 폴더는 어떻게 안전한가요?

자물쇠 비유가 아니라, 실제 원리를 차근차근 — 용어 하나하나가 왜 필요한지까지.

보안 폴더의 모든 안전은 딱 하나의 원리에서 나옵니다:
"공개키로 잠근 것은, 짝이 맞는 개인키로만 풀린다."
이 한 문장을 이해하면 나머지는 전부 따라옵니다.

0. 먼저 — 공개키와 개인키 (제일 중요)

암호화에는 두 가지 방식이 있어요. 보안 폴더의 뼈대는 비대칭 암호화입니다. 이게 핵심이라 먼저 짚습니다.

비대칭(asymmetric) = 잠그는 열쇠와 푸는 열쇠가 서로 다르다. 항상 한 쌍으로 만들어집니다:

📢 공개키 (public key)

잠그기(암호화)만 가능 · 풀기는 불가능

  • 푸는 능력이 없으니 아무에게나 줘도 안전 → 그래서 이름이 "공개"
  • 누구든 이 키로 "그 사람에게 보낼 데이터"를 잠글 수 있음
  • 서버에 그냥 공개로 보관

🔑 개인키 (private key)

풀기(복호화)만 가능 · 짝꿍 공개키로 잠근 것만

  • 공개키로 잠근 걸 푸는 유일한 열쇠
  • 이게 새면 모든 게 뚫리므로 절대 남에게 주지 않음
  • 그래서 안전하게 보관되어야 함 (아래 1번)
A의 공개키로 잠근 데이터 = 오직 A의 개인키로만 풀린다
우체통으로 비유하면 — 우체통 투입구(공개키)는 길에 있어 누구나 편지를 넣을 수 있지만, 꺼내는 열쇠(개인키)는 주인만 갖죠. "넣는 건 누구나, 꺼내는 건 주인만." 이게 비대칭 암호의 전부입니다.

🌐 잠깐 — 이건 인터넷의 기본 기술이에요

비대칭 암호는 우리가 만든 게 아니라, 현대 인터넷 전체를 떠받치는 표준 기술입니다. 짧은 배경을 알면 더 믿음이 가요.

왜 발명됐나 — "열쇠를 어떻게 안전하게 나눠 갖지?"

옛날 암호는 전부 대칭이었어요 — 잠그고 푸는 열쇠가 같죠. 그런데 멀리 있는 사람과 비밀을 주고받으려면 먼저 같은 열쇠를 공유해야 하는데, 그 열쇠를 보내는 길이 안전하지 않다면? (열쇠를 안전하게 보내려면 또 열쇠가 필요한… 닭-달걀 문제) 이걸 키 분배 문제라 불렀고, 수천 년간 풀지 못한 난제였습니다.

해결 — 1970년대의 혁명

1976 Diffie & Hellman — "잠그는 열쇠와 푸는 열쇠를 다르게 만들면 되잖아?" 라는 발상으로 공개키 개념을 세상에 발표. 키를 미리 나눠 갖지 않아도 안전하게 통신 가능해짐.
1977 RSA (Rivest·Shamir·Adleman, MIT) — 그 개념을 실제로 동작하는 방식으로 구현. 큰 수를 소인수분해하기 어렵다는 수학에 기반. 오늘날까지 널리 쓰임.
1997 재밌는 사실 — 사실 영국 정보기관(GCHQ)이 1970년대 초에 이미 비밀리에 같은 걸 발견했지만 기밀로 묻어뒀다가 이때 공개됨.

지금 어디에 쓰이나 — 사실 당신은 매일 쓰고 있어요

여기비대칭 암호가 하는 일
🔒 브라우저 자물쇠 (HTTPS)사이트 접속할 때마다 — 사이트가 진짜인지 확인 + 안전하게 통신 열쇠 교환
🎫 로그인 토큰 서명우리 워크스페이스 로그인 토큰(Better Auth JWT)도 비대칭 키로 서명해 위조 방지
💬 메신저 E2E시그널·왓츠앱의 종단간 암호화 — 우리 보안 폴더와 같은 원리
🖥️ 서버 접속 (SSH), 🪙 블록체인 지갑비밀번호 대신 키 쌍으로 로그인 / 지갑 주소가 곧 공개키
핵심 — HTTPS도 우리 보안 폴더도 같은 "하이브리드" 방식:
비대칭으로 "열쇠"를 안전하게 전달 → 그 다음 빠른 대칭 암호로 실제 데이터를 처리

우리 보안 폴더에서 vault_key를 공개키로 잠가 전달하고, 실제 파일은 빠른 AES(대칭)로 암호화하는 게 바로 이 하이브리드예요. 브라우저가 HTTPS로 하는 것과 똑같은 패턴입니다 — 검증된 방식이죠.

1. 개인키는 어디에? — 비밀번호의 역할

개인키가 그렇게 중요하면, 어디에 둘까요? 내 컴퓨터에만 두면 다른 기기에서 못 쓰고, 서버에 그냥 두면 위험합니다. 그래서 — 개인키를 "내 비밀번호로 잠가서" 서버에 보관합니다.

🧠비밀번호내 머릿속에만
(서버에 저장 안 됨)
→
⚙️튼튼한 열쇠로 변환비번을 암호용 열쇠로
(KDF)
→
🔒개인키를 잠금잠긴 개인키를
서버에 보관

그래서 서버는 "잠긴 개인키"를 갖고 있지만 풀 수 없습니다. 비밀번호가 없으니까요. 내가 로그인 후 비밀번호를 입력하는 순간, 내 컴퓨터에서 잠긴 개인키가 풀려 메모리에 잠깐 살아납니다.

그래서 비밀번호의 진짜 역할은 — "서버에 저장된 잠긴 개인키를 푸는 열쇠". 모든 사슬의 출발점입니다.

2. 열쇠 4개 — 각자 무엇이고, 왜 필요한가

🧠 비밀번호

역할서버에 저장된 잠긴 개인키를 푸는 열쇠 왜 필요모든 것의 뿌리. 이것만 머릿속에 있고 어디에도 저장 안 되므로, 결국 나만 풀 수 있게 됨

🔑 개인키 / 📢 공개키 (한 쌍)

역할공개키로 잠그고 → 개인키로 푼다. "나에게 안전하게 전달" 을 가능하게 함 왜 필요비밀(폴더 열쇠)을 직접 주고받지 않고도, 남이 내 공개키로 잠가서 줄 수 있게 → 공유의 토대

🟦 vault_key (폴더 마스터 열쇠)

역할그 보안 폴더 전체를 다루는 열쇠. 이게 있으면 폴더 안 모든 파일 열쇠(DEK)를 풀 수 있음 왜 필요공유의 핵심. 멤버마다 "각자 공개키로 잠근 vault_key 사본"을 줌 → 한 폴더를 여러 사람이 각자 비번으로 접근

🔴 DEK (파일 열쇠)

역할파일 하나하나를 실제로 암·복호화하는 열쇠. 파일마다 다름 왜 필요파일별로 분리해야 파일 하나만 따로 다루거나, 한 파일 열쇠가 새도 그 파일만 노출. 또 빠른 방식(대칭)이라 큰 파일도 빠름

3. 전부 연결한 사슬 (한 칸씩 푸는 순서)

보안 폴더 파일을 열 때, 위에서 아래로 한 칸씩 풀려 내려갑니다. 각 칸이 왜 있는지 함께 보세요.

🧠 비밀번호내가 입력. 이걸로 →
↓ 푼다
🔑 개인키서버의 잠긴 개인키가 풀려 내 메모리에 살아남. 개인키로 →
↓ 푼다
🟦 vault_key내 공개키로 잠겨 있던 vault_key를 풀어 폴더 마스터 열쇠 확보. 이걸로 →
↓ 푼다
🔴 DEK폴더 안 각 파일의 열쇠(파일마다 다름)를 풀어냄. 이걸로 →
↓ 푼다
📄 파일드디어 원래 내용이 내 화면에 복원됨.
이 모든 과정은 내 기기 안에서만 일어납니다. 서버는 잠긴 것들을 건네줄 뿐, 푸는 데 전혀 못 끼어듭니다 — 비밀번호가 없으니까요.

4. 그래서 "공유"란?

폴더 공유의 핵심은 vault_key 입니다.

다른 사람도 폴더를 보려면 vault_key 가 있어야 해요. 그런데 열쇠를 그냥 건네면 위험하죠. 그래서 주인은 — 받는 사람의 공개키로 vault_key를 잠가서, "이 사람도 vault_key를 풀 수 있다"는 권한을 DB에 등록합니다.

🙋주인vault_key 보유
→
📢동료 공개키서버에서 가져옴
→
🔒그걸로 vault_key 잠금동료 개인키로만 풀림
→
🗄️DB에 권한 등록동료의 잠긴 vault_key 사본

즉 "공유" = vault_key를 복호화할 수 있는 권한(잠긴 사본)을 DB에 추가하는 것. 그러면 동료는 자기 비밀번호 → 개인키 → 그 vault_key → 폴더 안 모든 파일의 DEK 순으로 풀어서 접근할 수 있게 됩니다.

멤버가 N명이면 각자의 공개키로 잠근 vault_key 사본이 N개. 같은 열쇠지만 각자 자기 비밀번호로만 꺼냅니다. 주인도 서버도 동료 것을 대신 못 엽니다.
단, 받는 사람이 먼저 보안 폴더를 한 번 설정해야 공개키가 생겨서 공유가 가능합니다.

5. 왜 굳이 여러 겹일까?

"비밀번호로 파일을 바로 잠그면 안 되나?" 싶죠. 층을 나눈 건 각 열쇠의 "단위"가 다르기 때문입니다.

열쇠단위층이 따로 있어 좋은 점
🔴 DEK파일마다파일 하나만 따로 다루기 / 한 파일 노출돼도 그 파일만
🟦 vault_key폴더(공유)마다멤버 추가 = vault_key 하나만 그 사람 공개키로 잠그면 끝 (파일 수와 무관)
🔑 개인키 / 🧠 비밀번호사람마다비밀번호를 바꿔도 개인키만 다시 잠그면 됨 (파일 전체 재암호화 불필요)
예: 멤버 추가 시 vault_key가 없다면 파일 1000개의 열쇠를 전부 그 사람 공개키로 다시 잠가야 합니다. vault_key 한 겹 덕에 딱 한 번이면 끝납니다.

6. 비밀번호와 복구 코드

이 비밀번호는 로그인 비밀번호와 다른 보안 폴더 전용 비밀번호예요. 잊으면? 서버는 도와줄 수 없습니다(애초에 모르니까). 그래서 처음 설정할 때 복구 코드를 딱 한 번 보여줍니다 — 잊었을 때 개인키를 푸는 비상 열쇠입니다.

⚠️ 비밀번호와 복구 코드를 둘 다 잃으면 → 개인키를 못 풀고 → 파일을 영원히 못 엽니다.
관리자도 못 살립니다. "아무도 못 본다"는 건 곧 "나도 열쇠를 잃으면 못 본다"는 뜻이에요. 복구 코드는 꼭 안전한 곳에 보관하세요.

7. 서버가 할 수 없는 일 (보안의 대가)

일반 폴더보안 폴더
파일 이름으로 검색 ✅불가 ❌ — 파일 이름도 암호라 서버가 모름
미리보기·썸네일 ✅없음 ❌ — 풀어봐야 알 수 있음
큰 파일 바로 열기 ✅전체를 받아 풀어야 열림 (조금 느림)
비번 분실 시 관리자 복구 ✅불가 ❌ — 복구 코드가 유일
그래서 보안 폴더는 정말 민감한 문서에 쓰고, 평범한 파일은 일반 폴더에 두는 걸 권합니다.
💡 다시 정리 — 비밀번호로 개인키를 풀고, 개인키로 vault_key를 풀고, vault_key로 DEK를 풀고, DEK로 파일을 엽니다.
그리고 공유 = vault_key를 상대 공개키로 잠가 DB에 등록하는 것. 이 사슬 하나가 전부입니다.
